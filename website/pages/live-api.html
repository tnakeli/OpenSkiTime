Overview

When an organizer publishes a race with OpenSkiTime, anyone can read it: in the browser, or with this API. The hosted service is https://live.openskiti.me. The local live timing of a race computer offers the same API, by default at http://localhost:5078 and only on that computer. Anyone can also run a server of their own.

There are two ways to read a race:

  • HTTP lists the published races and returns the complete state of one race.
  • SignalR sends every change as it happens, over one WebSocket connection.

The API is read-only. It tells what the organizer publishes now; it is not a results archive. All results are unofficial.

Machine-readable descriptions: OpenAPI 3.1 of the HTTP part and JSON Schema of every message. For AI coding tools, one text file has this page, the schema and the example readers.

Quick start

List the races published now:

curl https://live.openskiti.me/api/sessions

Follow one race with the JavaScript reader, using a sessionId from the list:

npm install @microsoft/signalr@10
node live-reader.mjs https://live.openskiti.me SESSION_ID

It prints what happens in the race:

Race | Synthetic slalom | 40 competitors
Run 1 | 1 TEST Anna | OnCourse
Run 1 | 1 TEST Anna | Intermediate 1 25.01
Run 1 | 1 TEST Anna | Finished 50.12, rank 1
Run 1 | 3 EXAMPLE Maria | DNS

The same reader is available for .NET and Java. All examples on this page are synthetic.

HTTP requests

RequestAnswer
GET /api/sessionsThe races published now, newest race date first. An empty list when there are none.
GET /api/sessions/{sessionId}/stateThe complete state of one race. 404 when the server has no state for the ID.

Recognize a race by its codex, or by date, name and discipline: a race that is published again can get a new sessionId.

The hosted service sleeps when nobody uses it, and the first request can take a couple of minutes. Use a timeout of two minutes for the first request. Do not send the X-OpenSkiTime-Live-Protocol header; it belongs to publishers.

  • Times are integers in hundredths of a second: 5012 is 50.12. Do not convert them to floating point for calculations, and do not calculate times from the source ticks, which are diagnostic.

Changes in real time

Connect a SignalR client with the JSON protocol to /live and invoke WatchSync(sessionId, 1). The number is the version of this protocol. One connection follows one race. The server then sends three messages:

MessageWhen and what
SyncThe answer to WatchSync and Resync, and whenever a change does not fit in a delta. The complete state when status is Live.
DeltaOne change: the complete new result rows of the competitors it concerns.
BeaconAbout every 30 seconds: what a reader that missed nothing has now.

The status of a Sync or Beacon is Live, Deleted (the organizer deleted the race) or Awaiting (the server has no state: the race is not published yet, the server has restarted and waits for the publisher, or the ID is unknown).

The server also sends Radio and Viewers to its own race page. They are not part of this API; ignore them and any other message you do not know.

Synchronization rules

The server sends the messages of a race in order. A reader keeps the state with its generation and revision, and follows these rules:

  1. Sync is always the newest. Live: replace the state, generation and revision, whatever they were. Awaiting: forget the generation and revision but keep the state, as the publisher normally restores it. Deleted: drop the state and disconnect.
  2. Delta applies only when its generation is yours and its baseRevision equals your revision. Ignore a delta of your generation whose revision is not newer than yours. Anything else is a gap.
  3. Applying a delta: in each listed run, every row in results replaces the row with the same bib, or is added at the end. If order is given, put all rows in that order; it must list every row once. If forerunners is given, it replaces the list. Then take version, updatedAt, paused and revision from the delta. If a run is unknown or the order does not fit, change nothing and treat it as a gap.
  4. Beacon should agree with what you have. If the status, generation or revision differs, treat it as a gap.
  5. After a gap wait a random 0.5–5 seconds and send Resync(), at least 3 seconds after the previous one. Ignore deltas until the Sync arrives. If it has not arrived in 30 seconds, ask again at the next beacon.
  6. After a lost connection connect again and invoke WatchSync, waiting 1 second at first and doubling the wait up to 15 seconds, with a random part. Keep showing the previous state until the new Sync, and ignore deltas and beacons before it.

Generations have no order; compare them only for equality. Do not use version for synchronization.

From changes to events

The API sends results, not events. Compare the rows before and after each Delta and each Sync; a row or run you did not have counts as Ready:

Change of a rowEvent
status becomes OnCourseStarted
New number in intermediatesIntermediate time
status becomes FinishedArrived at the finish; time and rank are in the same row
status becomes DNS, DNF, DSQ or NPSClassified
hundredths of a finished row, or an intermediate time, changes or disappearsCorrected
Only rank, difference or totals changeSomeone else’s result moved this row
  • The first Sync is the starting point, not a set of events.
  • A result can change afterwards, in any direction: a finisher can be disqualified, a DSQ can be cancelled, a time can be corrected, and a competitor with a re-run goes back to OnCourse.
  • The latest state is reliable, every step on the way is not. After a break in a connection, several changes can arrive as one: a competitor can go straight from Ready to Finished.

Polling

Without a SignalR client, for example in PHP, read GET /api/sessions/{sessionId}/state every 10 seconds while the race is on, never more often than every 5 seconds, and compare the rows as above. One background job should poll for all your users. The answer is always the complete state, some tens of kilobytes for a hundred competitors; there are no conditional requests.

  • 404: the race is not available now. Keep the last results and try again less often, for example every 30 seconds; give up after a while.
  • 429 or a network error: wait longer before the next request, up to a minute.

JavaScript, .NET, Java

The three readers do the same: without a session they list the races, with one they follow it until it is deleted. They recover from lost messages, broken connections and server restarts, and the project tests them together against the real server. They are on GitHub, free to use under the MIT license.

SignalR clients for other languages work too, if they support the JSON protocol.

Limits and fair use

  • Connect from a server or an application, once per race, and pass the results on to your own users yourself. The connections of the hosted service are shared with the spectators of every race.
  • Connect for the race, not around the clock. A connection or a poll keeps the service awake. Disconnect when the race is over or deleted, and if it stays Awaiting or paused for long. To find a race, read the list every few minutes around its start time.
  • Web pages of other sites cannot call the API directly. The server sends no CORS headers.
  • Limits of the hosted service now: 1000 simultaneous connections in all, 200 from one address, and 3000 requests per minute from one address. They can change. A request over a limit is refused with 429.
  • The state is in the memory of the server only. It disappears when the organizer deletes the race, when the publisher does not restore it after a restart, and in any case within 14 days of publishing. Store what you need.
  • The service is free and comes without an availability guarantee.

Versions and stability

This is version 1 of the Live API: the two HTTP requests, WatchSync with version 1, Resync, and the messages Sync, Delta and Beacon. It works with live timing server 0.10.0 and later, and with the local live timing of OpenSkiTime 0.3.0 and later.

  • Compatible additions can come at any time: new properties, new status values and new messages. Ignore what you do not know, and show an unknown status as no result.
  • An incompatible change gets a new version. It is announced in the changelog of the live timing server beforehand, and the previous version keeps working for a transition period.
  • Publishing, race radio, server statistics and everything else not described here can change without notice.

Personal data

Races contain names, clubs, nations and results of competitors, who are often children. The organizer decides what is published here and for how long. You are responsible for what your service does with the data: agree on it with the organizer, show the results as unofficial, and follow corrections and deletions.
