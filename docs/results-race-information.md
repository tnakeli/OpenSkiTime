# Results race information and optional lookups

Results and Timing report use the shared active competition selector in the window header. Their navigation buttons also open a flat competition menu, with a dot and **ACTIVE** beside the selected competition. These views select a whole FIS competition and show no run submenu. Entering either view from SL1 Run 2 keeps SL1 selected; returning to Timing for the same competition retains Run 2. Switching competition in either review view also updates the other view when opened.

Post-run review (2026-10-02): Timing provides an **Edit classification** panel for DSQ/DNF and other final statuses, with optional DSQ gate, reason/ICR reference and judge. Corrections survive reopening and are audited together. FIS XML carries gate/reason; judge identity remains local. Weather may also retain an air temperature whose measurement place is unspecified; XML omits `Place` for that record. See [post-run classification review](post-run-classification.md).

Reviewed 2026-10-02. Results is ordered **Race information → Penalty calculation → XML file**. Race information can be prepared and saved before a start list or timing exists. The Results form edits chief of race, referee, course chief, start referee and finish referee; the shared technical delegate is edited in Competitions and displayed read-only in Results; each configured run has its own course setter, course, homologation, elevations, drop, length, gates, turning gates, start time, forerunners, conditions, snow and measured start/finish air temperatures. Add/remove forerunners independently for each run. Identifiers initially use A–Z, then F27 onwards, and may be edited.

New run fields start from the saved Competition course details. Location comes from shared competition calendar data, falling back to the series location. Saved run overrides are independent of subsequent course edits. Surnames and nation codes are normalized to uppercase on save. Incomplete drafts are allowed; entered numbers, times, nations and forerunner identities are validated before mutation. Race information saves automatically after a 400 ms pause in editing. There is no save button. Valid incomplete names and partial forerunner rows are saved; invalid numbers, incomplete nation codes and invalid start-time text remain visible with a **Not saved** message until corrected. Final XML approval still requires complete people and run fields. Valid changes are queued per competition so switching races cannot write to the wrong race. Close, event-file switch, creation, backup, series/competition save and XML approval flush pending writes; invalid or failed saves block close/file switch rather than silently losing edits. Refreshing timing preserves the current form.

In **Competitions**, **Save Course & Homologation to all <discipline> races** (for example **Save Course & Homologation to all Giant Slalom races**) appears above **Save competition**; its label follows the discipline selected in the form. When checked, saving an existing or new competition also replaces the course name, homologation number, start/finish altitudes, vertical drop and course length in every other competition of the same discipline in the current series, including local races. Competitions of other disciplines keep their own course and homologation. Blank course fields explicitly clear the corresponding values in the matching races. Other competitions retain their names, dates, disciplines, categories, codices and run counts. The edited competition and all shared course changes validate and commit in one transaction; validation, revision or database-constraint failures leave every race unchanged. The checkbox defaults to unchecked and resets after a successful save, competition selection or new-competition action. Saved per-run course overrides remain independent.

The Competitions grid's **Homologation** column includes the saved start and finish altitudes, for example `123/10/26 500m - 300m`. A missing altitude is displayed as a dash; if both altitudes are absent, only the homologation number is shown. This presentation does not change the saved homologation number or per-run course overrides.

**Save TD to all races** sits to the right of the course-sharing checkbox above **Save competition**. It independently copies the edited technical delegate's surname, first name, nation, number and original-name review text to every competition in the current series, including local races. Blank TD fields explicitly replace the corresponding destination values. Each destination retains its other calendar metadata, including season, category, gender, location and nation. A race without calendar metadata receives an empty calendar record with its date-derived season when needed to store the TD. Both sharing options can be selected together and commit with the edited competition in one transaction. Validation, revision or database-constraint failures preserve every race. The TD-sharing checkbox is initially unchecked and resets after successful save, selection change or new-competition action. **Get competition data** saves only the selected competition, regardless of these sharing checkboxes.

New competitions default to **FIS**, and the race-type picker uses that capitalization. An existing Club competition can be changed to FIS even after drawing or starting a run; a FIS code is required. Race-type changes update competition metadata without rewriting saved start lists, bibs, draw inputs or timing history. Date, discipline and run count remain protected after drawing. Non-FIS competition forms hide FIS code and homologation, while preserving their stored values; start-list views hide FIS points and list descriptions. FIS race information, penalty and XML sections are hidden when no FIS competition is selected. The series-wide Competitors lookup remains available because athlete details can also be used for local competitions.

Race information is stored as immutable numbered revisions in the portable `.ost` database. TD approval commits the current race information revision, its approval snapshot and the exact XML bytes in the same transaction. Later edits create history without changing prior approvals. New development files are created directly from the current model. Incompatible older development files are rejected without modification; create a new series file. Database migrations are deferred until releases begin. No credentials or downloaded athlete archive are embedded in these records.

## FIS public API analysis

Reviewed against the live [Public API OpenAPI document](https://api.fis-ski.com/public-docs?public-api-docs.json) and [public Swagger documentation](https://api.fis-ski.com/documentation/public?urls.primaryName=Public+API+fis-ski.com). The general OAuth2 API is restricted to FIS-issued clients and is excluded from this application. No general API request, OAuth setting, sign-in or token-refresh flow is implemented. The same saved Member Section API key is used for XML uploads with bearer authentication; it is not a general API OAuth credential.

| Public endpoint | Available information | Documented operation authentication |
| --- | --- | --- |
| `/competitions/find-by-codex/AL/{codex}?season={season}` | ID/event ID, codex, place/nation, season/date, category, event, gender, cancellation/official/points eligibility flags, published applied penalty, result/start-list/PDF availability, live links | `X-Api-Key` |
| `/athletes/find-by-fis-code/AL/{fisCode}` | Athlete identity, nation, birth data, club, optional points using `includeFisPoints=true` and `effectiveDate` | `X-Api-Key` |
| `/athletes/find-by-name` | Up to 30 name matches, with optional discipline filter | `X-Api-Key` |
| `/fis-points-lists/AL/{season}?type=normal` | List IDs/names, numbers, validity and calculation dates; filters include effective date | `X-Api-Key` |
| `/data-feeds/fis-points-lists/normal/AL/download` | Normal points ZIP by effective date; also download-by-ID endpoints and base lists by season/ID | No operation-level security declared; feed access rules remain separate from JSON lookups |
| `/homologation/course/AL` | Course/certificate IDs, name, nation, start/finish elevations, vertical drop, length, event/gender and validity; exact-code/place/nation/event/gender/validity filters | No operation-level security declared; actual access unverified |
| `/homologation/timing-devices` | Approved device models/manufacturers, codes, categories and expiry filtering | `X-Api-Key` |
| `/data-feeds/calendar`, `/data-feeds/competitors` | Bulk ZIP exports, optional export date | No operation-level security declared |
| `/sanctions/AL/{season}`, `/status/result` | Sanctions and result status code definitions | No operation-level security declared |

The public competition JSON does **not** contain jury, course setters, forerunners, gates, run start times or run weather. Result availability is a flag, not result rows. However, the public **calendar ZIP** contains additional shared event and assigned technical delegate fields. This distinction is important: absence in JSON does not imply absence across the public API.

## Shared competition data and Get competition data

**Event series → Browse FIS calendar** downloads the latest public `/data-feeds/calendar` ZIP once, using the saved public API key. Season defaults from the series. Column headers use the same separate sort and text-filter buttons as Competitors. Filters match every entered word without case sensitivity and combine across columns. Enter or Apply accepts the filter; Cancel or Escape discards the draft. Clicking an active filter clears it, and an arrow marks ascending or descending sorting. Clear filters resets all column filters. The series nation is an initial, visible nation filter. Race counts sort numerically and dates chronologically. Click a column title or its sort arrow to toggle ascending/descending order; Start and End use the underlying date values across month and year boundaries. A still-visible event selection and its preview are retained; filtering the selected event out clears selection so a hidden event cannot be imported. Separate nation/search fields have been removed and the compact season toolbar leaves more vertical space for events. `A_event.csv` is joined to `A_raceal.csv` by event ID and season. Only supported SL, GS, SG, DH and AC races are included; duplicate event/codex identities and malformed archives are rejected. The browser previews event dates, location, nation, event name, race codices, disciplines, categories, gender and TD fields before **Use selected event**.

New calendar competitions use short names such as **SL1 W 4.1**: discipline, competition number, gender and day/month without leading zeros. Numbering starts at one for each discipline/gender within the selected event, ordered by race date and then codex for same-day races. Competition event names append discipline, expanded gender (Women, Men or Mixed) and the four-digit codex to the supplied FIS event name, for example **Synthetic weekend - SL Women 0797**. If the event name is missing, the race location is used as the base. The FIS event name's capitalization is preserved. Reimport keeps existing local short names.

The series receives event name (or location if absent), place, nation, season and event start/end dates. Organizer is prefilled from the FIS organizer contact's first address line (`OrgaddressL1`) when supplied and remains editable; an absent organizer must be filled manually for a new series. Each competition receives date, event name, discipline, FIS codex, season, location, nation, category, gender, supplied TD fields and supplied homologation number. New DH/SG races default to one run; other supported races default to two. Course geometry, setters, forerunners and weather are not inferred from this export.

On acceptance, one public codex lookup per selected race verifies event/season/codex identity, date, discipline, nation, category, gender against the preview. A FIS cancellation flag alone does not block importing competition metadata or local registration, start lists and timing; competition/race-information lookups show it as informational status. A mismatch rejects the selection without changing data; no second calendar ZIP download or OAuth2 endpoint is used. A new series stages the reviewed competitions until **Create series file**, which writes series and competitions into the temporary database before publishing the file. For an open series, the complete import saves in one transaction and matches existing FIS races by season/codex, keeping their IDs. Unrelated competitions remain. Missing values and local course geometry, labels, run/intermediate counts are preserved; a missing TD number is preserved only for the same delegate identity. Ambiguous matches, label conflicts, stale revisions and changed date/discipline after drawing reject the complete import. Fetching remains optional; manual offline setup works as before. No schema change or migration is needed for this feature.

Tests cover the public download and joining boundary with synthetic archives, unsupported disciplines, duplicate/cancelled races, whole-event creation and reopening, repeated imports, rollback on conflicts and drawn-race changes, actual UI selection/filtering/creation/refresh, and stale responses after starting another series. Credentials in UI tests use an in-memory credential store, without reading or modifying the user's Windows credential.

New Event Series forms prefill the season from the local computer date, using the FIS June boundary (for example, 2026-10-02 → `2026/27`). New competitions inherit the FIS season from the saved Event Series season (`2025/26`, `2025–26`, `2025-2026` → 2026; a single year is used as entered). A competition-specific saved season takes precedence. Entering an empty Competitions view opens the new-competition editor automatically and preserves its draft when navigating away and back. All four date-picker flyouts display `MM MMMM yyyy` and update this label when navigating months.

The FIS season, codex, location, nation, calendar category, gender and technical delegate (surname, first name, nation, number) are edited under **Competitions**, alongside the public/event name and discipline. **Get competition data** needs season and codex; it makes one authenticated public codex lookup and one calendar ZIP request. It stages the complete validated data and uses the existing transactional competition save. Results no longer contains a category editor, fetch button or manual race-information save. The editable **FIS category** field sits beside Discipline and accepts calendar category codes such as NJR, FIS and NC; saving normalizes the code to uppercase. The separate **Use FIS rules** checkbox selects the competition rule type and is checked for new competitions. Clearing it selects a local (Club) competition, disables the category editor and hides the other FIS controls while retaining stored FIS values. It does not select or overwrite the calendar category. Local race code has been removed from the UI, domain model and database.

The JSON lookup supplies place, nation, category, event code, gender, date and race/event IDs. `/data-feeds/calendar?date=yyyy-MM-dd` supplies `A_raceal.csv` and `A_event.csv`. The selected archive date is the earlier of the race date and explicitly supplied current UTC date, which avoids requesting a future archive. The alpine table joins by season/codex and confirms race ID, event ID, date, event, category, gender and nation against JSON. The event table joins by event ID, season and AL sector. It supplies `Eventname`; the race table supplies `Td1name`, `Td1nation`, `Td1code`. Ambiguous joins and mismatches reject the entire fetch before editor mutation. Missing columns/rows or oversized/invalid ZIP data are not guessed.

The TSV export uses NUL-delimited cell values in actual downloaded archives; the bounded parser removes these delimiters without extracting ZIP entries to disk. TD display names are surname first and may have a parenthesized nation suffix. Two-word names or comma-separated surname/first-name pairs populate separate fields. Compound names remain visible as an original-name review field rather than inventing a split. A TD number is retained in this case, but separate names must be entered before XML approval. TD names and nations are imported even when the calendar has no assigned TD number. An existing TD number is preserved only when the imported surname, first name and nation match it; a different TD never inherits the old number. If the calendar has no TD identity, existing TD fields are preserved. Missing event names preserve entered names; a new unnamed race gets a clearly local place/event fallback.

Shared data is a typed `CompetitionCalendarData` contract on `CompetitionValues`, persisted as `Competitions.CalendarJson` in the portable event database. These fields are included directly in newly created development databases. Historical approval snapshots retain their exact stored XML within compatible files. New XML uses shared location/nation/category/season, public name, discipline, checked gender and TD, including `<Jury Function="TechnicalDelegate"><Number>…</Number>`. Results displays the shared TD read-only; other jury members remain editable there. The same domain contract is available to future timing-report/live-timing features; those features are not implemented by this change.

The existing API key is reused and stays in Windows Credential Manager. Only explicit browse/get actions start network fetches; offline edits and race-information autosave do not require online access. The general OAuth2 API remains excluded. Public calendar exports were fetched live both for the current export and 2026-03-21. The actual reader successfully parsed event name and TD name/nation/number for an assigned race from the latter archive. For the supplied AL/5573/2026 example, the dated archive matched the race and contained the TD display name and nation, but no event name or assigned TD number. The previous reader incorrectly discarded the TD identity when its number was blank; this is fixed. Subsequent 2026-03-22, 2026-03-25, 2026-04-01 and 2026-05-01 public archives also lacked that TD number. The public FIS event-details page did contain the number shown in the user screenshot; it is a separate web source, not a documented public API endpoint. Availability therefore depends on the calendar data; the application must preserve manual values rather than claiming every codex has all requested fields. No real race response or TD information is committed as a fixture. Authenticated JSON lookup remains unverified.

The [TimingReport user manual](https://assets.fis-ski.com/f/252177/x/747c65b7b6/timingreport_user_manual.pdf) confirms its **Get competition data** autofill behavior; it does not establish that TimingReport uses this exact public endpoint. The implementation above uses only documented public API routes and verified public export columns.

## Course homologations

Course and homologation details are always expanded in the competition editor. **Browse FIS homologations** calls the documented public `/homologation/course/AL` endpoint with escaped location, event code and nation filters. It reads bounded paginated JSON from the fixed API origin, ignores response-provided navigation URLs and filters by the competition date and gender, including gender `A`. Historical competition dates are checked against `validFrom`/`validTo`; today's validity is not substituted. Missing/invalid data and network failures preserve existing editor values.

A single matching course fills the editor. Multiple matches require choosing a course and **Apply homologation**. Course name, certificate number, start/finish elevations, vertical drop and course length remain editable and are persisted by **Save competition**. Changing the location/date/event makes an old selection inapplicable until browsing again. A live unauthenticated public lookup for Ruka/SL/FIN returned Slope 4, certificate 14679/11/22, elevations 498/317 m, drop 181 m and length 640 m. No downloaded race or TD data is used as a committed test fixture.

Results inherits these values for each run. Race-information revisions retain the competition defaults used while editing; fields matching those defaults follow later competition edits, while differing per-run values remain overrides. This allows Run 2 to retain a different start elevation. XML uses the effective per-run course values and length. Existing saved approvals and race-information revisions are not rewritten by a competition edit.

The competition grid adds codex, category, gender, location, course, homologation and TD surname/number and selects a single competition for editing. Column filtering and sorting use the same controls as Competitors; dates and numbers sort by their typed values. Changing sorting or filtering preserves the selected competition and unsaved editor fields while it remains visible. Redundant section titles above the grid are removed. The Copy from competition functionality has been removed. The initial FIS season/codex and optional lookup guidance text is hidden; status messages appear only during a lookup or when it has a result or error. Browse FIS homologations is left-aligned below the course-section heading.

The development database format is now `OpenSkiTime.Development/3`, including competition course length and removal of local race codes. Create a new file for incompatible earlier development formats; no migration is implemented. Tests cover public course filters/pagination, selection through the actual UI, manual changes reaching Results, per-run overrides after changing defaults, season defaults, the FIS checkbox and all date-picker flyouts. Native Windows interaction and authenticated competition retrieval remain separate checks.

## XML test submission

Contract reviewed from the supplied `C:/Users/tniem/Downloads/schema.yml` (FIS Member API, OpenAPI 3.0.3). Server: `https://profile.fis-ski.com/api`. Upload: `POST /results/competition-files/upload`; status: `GET /results/competition-files/status/{uuid}`. Authentication is a **Member Section personal access token**, with `competition.files.write` and `competition.files.read` permissions. Settings now stores one shared FIS API key for data access, homologations and XML uploads. Uploads send this key as a bearer credential; public JSON APIs retain their documented X-Api-Key header. The duplicate lower credential field has been removed. General OAuth2 access is never used.

**Send XML · test mode** submits the selected immutable approval's exact filename and bytes as one multipart `files[]` part, plus hard-coded `testMode=true`. There is no production toggle or production method. XML is restricted to 2 MB; unsupported/unsafe filenames are rejected locally. Neither the codex nor the approved XML is rewritten for testing. The response must explicitly confirm `testMode=true` and supply a valid UUID, summary and file list before it can be reported as a supported response.

The supplied contract says test mode runs validation without persisting competition files or forwarding them for result processing. Test submission status is ephemeral for 24 hours. Reserved codex **9991** simulates success, with XML initially accepted and processed about 60 seconds later; **9992** simulates lack of race permission. Any other codex simulates an unknown race. Thus a normal competition XML is expected to receive a test rejection even if its structure is valid. To exercise success, create a separate synthetic competition with codex 9991 and approve its XML normally.

The UI shows UUID, summary, per-file state/comments and the returned JSON, including validation failures. JSON is displayed as plain text, bounded to 1 MB, and exact token echoes are redacted. Responses are never written to diagnostic logs. Status URLs returned by the server are not followed: authenticated GETs use the fixed documented HTTPS origin and UUID path, and redirects are disabled. This also resolves the contract's example `api.fis-ski.com` status URL versus its declared `profile.fis-ski.com/api` server without exposing the credential to arbitrary URLs.

Automatic polling uses at least five seconds between requests, sharing a client limiter across all submissions and respecting status `Retry-After`. It stops on `summary.isComplete`, error, operator cancellation or after two minutes. **Check status** resumes polling using the displayed UUID; an operator can paste an earlier test UUID after restarting. Stop waiting cancels local waiting, not a remote accepted upload. No POST is automatically retried, including timeout or uncertain network failures.

Submission displays are associated with the event path and approval ID in session memory so switching revisions/races does not show another race's response. They are not durable event history; retain the UUID to resume after restarting. The approved XML and approval history remain durable in the portable event database. Timing capture is independent of optional online work.

Live authenticated upload/status and FIS acceptance of the generated XML remain unverified. Tests cover multipart field names, exact bytes, mandatory test mode, bearer authentication, fixed status origin, completion, HTTP validation/authorization/expiry failures, malformed/non-test responses, mismatched UUIDs, no POST retries, five-second cross-submission polling, Retry-After and cancellation.

## Existing FIS points list

No new points-list download is needed. Results initially uses the same cached-list display as Competitors: `code: name (dd-MM-yyyy)` and `Effective yyyy-MM-dd–yyyy-MM-dd`. Once timing results are assembled, the drawn list's code and validity are authoritative. If the local cache is a different version or unavailable on another computer, display the drawn snapshot explicitly instead of describing a different downloaded list. Race points and penalty use the saved starter points. Number of competitors, distinct represented nations and the existing 2026/27 discipline F value are calculated from the reviewed race.

Penalty parameters now come from the downloaded list's `cat.csv` and `dis.csv` tables, joined to the alpine race level in `Fiscategory.txt`. Category, discipline and gender select the minimum, maximum, F factor, points cap, correction Z and race-level adder. Results displays these values and the exact list validity as read-only information; calculation runs automatically when complete results load. No operator-entered penalty parameters or assumed category defaults are used. See [FIS penalty review](fis-penalty-review.md).

## Optional weather browser

[Open-Meteo geocoding](https://open-meteo.com/en/docs/geocoding-api) searches the existing location text and presents candidates with coordinates, region/country and timezone. The operator selects a location, then explicitly requests [hourly forecasts](https://open-meteo.com/en/docs) with `temperature_2m`, `weather_code`, `timezone=auto` and a 16-day forecast window. Only the competition date's local hours are offered. Each run can select a different hour. Unsupported dates and network failures preserve manual fields.

Applying an hour fills an empty conditions field and stores the forecast temperature, local timestamp/timezone, fetch timestamp and source URL in that run's weather provenance. It preserves entered conditions and snow and does not put a grid-cell model temperature into measured start/finish fields. Snow hardness and the two measured temperatures remain manual. Open-Meteo attribution is shown in the browser; its data are licensed under CC BY 4.0. Selected provenance travels with the series and approval snapshot; browsing candidates are transient.

## XML and verification boundary

The [Alpine XML description 2.12](https://assets.fis-ski.com/f/252177/x/c9387bbcb5/result-xml-alpine.md), sections 2.2 and 2.3.1–2.3.9, supplies jury function spelling, length/temperature units, course fields, sequential numeric forerunner `Order` and weather element names. User-facing forerunner IDs remain in the report snapshot; XML uses their list positions. Measured temperatures are emitted as weather records labelled Start and Finish. Forecast source URLs and forecast temperatures remain in the approval snapshot rather than masquerading as measured XML values. The authenticated XML test service has not been exercised; acceptance of multiple weather records per run remains an integration check for FIS/TD review.

Tests exercise API request paths/authentication, identity mismatches, HTTP failures, forecast date/timezone/null handling, invalid/conflicting persistence, immutable history, backup/reopen, incompatible-file rejection without mutation, approval snapshot/reopen, XML metadata, competition-specific drafts, actual jury-cell editing and forecast-button binding. Headless renders cover race information, run details, penalty and XML sections.
