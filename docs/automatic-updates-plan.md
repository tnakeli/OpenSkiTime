# Automatic updates implementation plan

Agreed 2026-11-26; not implemented yet. OpenSkiTime checks openskiti.me for a newer release, downloads the signed installer from GitHub Releases when the operator asks for it, and installs it with the existing Inno Setup installer when the operator clicks **Restart to update**. The application then starts again with the event series that was open. Nothing is installed without that click. The design is deliberately small: one static file, one download, one list of trusted signers, the existing installer, no channels and no new dependencies.

## Decisions

| Topic | Decision |
|---|---|
| Installation | Only after the operator clicks **Restart to update**. Never automatic, never on exit, never at startup. |
| Update check | Always on; there is no setting. The About privacy text and the website privacy page say so. |
| Mechanism | The application checks, downloads, verifies and launches; Inno Setup installs. The full installer (about 290 MB) is downloaded for every update. No delta updates, Velopack or MSIX. |
| Race state | No update-specific rules. **Restart to update** closes the window through the normal close path; whatever closing allows or refuses, updating does too. |
| Series files and other computers | No update logic. The release notes say when a version upgrades series files; operators update their own computers. |
| Bad releases | No withdrawn or important flags. A bad release is fixed by a new release. The existing release-process step of marking it as a prerelease also removes it from the manifest at the next website deployment. |
| Channels | None. The manifest offers only the newest stable `vX.Y.Z` release. Previews are GitHub releases that the manifest never offers; a computer running a preview is offered the next stable version. |
| Source of update information | A static manifest on openskiti.me, generated by the website build. The installer and release notes come from GitHub Releases. The application never polls the GitHub API. |
| Publication | The manifest changes in the website deployment that already follows every published release. |
| Signer | The downloaded installer must carry a valid Authenticode signature whose certificate thumbprint or common name is listed in `deploy/windows/update-signers.txt`, which is built into the application. A new certificate is added to the list in a release before it is used (see [Certificate changes](#certificate-changes)). |
| Download | Starts when the operator clicks **Download update**, not in the background, so 290 MB never surprises a venue's mobile connection. |
| Release notes | Not copied into the manifest. **What's new** opens the GitHub release page of the offered version. |
| Copies the installer did not install | The portable ZIP and development builds show the new version with a link to the download page instead of installing it. |

## Update manifest

`https://openskiti.me/updates/v1/latest.json`:

```json
{
  "version": "0.6.0",
  "windowsInstaller": {
    "size": 290898632,
    "sha256": "<64 lowercase hex digits>"
  }
}
```

- `website/build.mjs` writes the manifest from the release that `scripts/read-release.mjs` selects, but only when that release is stable (`vX.Y.Z`, not a prerelease) and has the installer asset. `size` and `sha256` come from the asset's `size` and `digest` (`sha256:<hex>`) in the release data the build already reads. A missing or non-SHA-256 digest fails the build instead of quietly publishing no update. When the site falls back to a preview because no stable release exists, no manifest is written.
- The manifest contains no URLs. The application derives the installer URL `https://github.com/tnakeli/OpenSkiTime/releases/download/v{version}/OpenSkiTime-{version}-win-x64-setup.exe` and the release page `https://github.com/tnakeli/OpenSkiTime/releases/tag/v{version}` from the validated version. Network data therefore never decides what is downloaded or which address is opened.
- `website/check.mjs` verifies the manifest against the release file (version, size, digest) and verifies that no manifest exists for a preview. `website/staticwebapp.config.json` serves `/updates/*` with `Cache-Control: no-cache`.
- Installed versions read `v1` for years. Unknown properties are ignored, so fields can be added later. A change that older versions cannot read, such as a new asset name or a new required field, goes to `/updates/v2/`, and `v1` keeps being produced.
- Publication needs no maintainer step. `windows-sign.yml` already runs the website deployment after the release is public, so the manifest never points to an installer that is not yet published.

## Checking for updates

- The application checks about 30 seconds after the main window opens, whenever Settings → About is opened, and when the operator clicks **Check now**. There is no other schedule.
- Each check is one HTTPS GET of the manifest with a short timeout, no redirects, a 16 KB response limit and strict typed parsing. The request carries no cookies or query string. Its User-Agent is `OpenSkiTime/<version>`.
- An update is offered when the manifest version is newer than `ProductInfo.Version` by Semantic Versioning precedence; for example, `0.6.0` is newer than `0.6.0-preview.2`. An equal or older version is never offered, so the updater never downgrades.
- A failed check (offline, timeout, error status, invalid file) appears only in About as `Could not check for updates`, with the time of the last successful check. It produces no dialog, chip or status-line error. Checks run off the UI thread and never delay startup, rendering or capture.

## Downloading and verifying

- **Download update** streams the installer to `<local data>/Updates/OpenSkiTime-{version}-win-x64-setup.exe.partial`. The local data folder comes from `LocalDataDirectory`, so `OPENSKITIME_LOCAL_DATA` redirects it. About shows the progress, and the download can be cancelled.
- Downloads use HTTPS only. Redirects are followed, because GitHub redirects to its asset host, but never to HTTP. The download stops if more bytes arrive than `size`. The SHA-256 is computed while streaming. There is no resume: a failed or cancelled download is deleted and starts again.
- Before the file gets its final name, every check must pass:
  1. Size and SHA-256 equal the manifest.
  2. `WinVerifyTrust` accepts the file's Authenticode signature: intact, and chained to a trusted root. Revocation is not checked, so updating never depends on reaching a CA's revocation servers.
  3. The signer certificate's SHA-1 thumbprint, or its common name (the *Name* Windows shows in Digital Signature Details), is listed in `update-signers.txt`.
  4. The installer's product version equals the offered version exactly, including any pre-release label (`0.6.0`, `0.6.0-preview.1`).
     - `installer.iss` sets it with `VersionInfoProductTextVersion={#AppVersion}`. The numeric file version `X.Y.Z.0` cannot tell a preview from its stable release.
     - The signature covers the version resource, so an older or preview installer published under another version's name is rejected.
     - Inno Setup itself would overwrite newer files (`ignoreversion`).

  A failure deletes the file and shows `The update could not be verified`, with the reason and a link to the download page.
- A file under its final name has passed these checks. Later steps (the next start, **Restart to update**) only re-check its SHA-256 against the manifest. `Updates/` keeps at most the installer of the offered version. Other installers and partial files written by the updater are deleted at startup.

### Why the signer is checked

The manifest follows automatically from any published GitHub release. The application runs the downloaded installer itself, so Windows shows no download warnings (the file has no Mark-of-the-Web). The per-user installation also needs no UAC prompt. Without check 3, control of the GitHub repository would be enough to run code on every race computer that clicks **Restart to update**. With the current Certum certificate, an attacker also needs the cloud signing key and the maintainer's one-time SimplySign code.

## Trusted signers

`deploy/windows/update-signers.txt` is embedded in `OpenSkiTime.Desktop`. Each line is either a SHA-1 thumbprint (40 hex digits, case and spaces ignored) or a certificate common name, compared exactly. Lines starting with `#` and blank lines are ignored.

```text
# Installers signed by any of these certificates are accepted by the updater.
# A line is a SHA-1 thumbprint or a certificate common name.
Open Source Developer <maintainer name>
1D3DB65248381C9A41DC006392ECBA30CA21A8B8
```

`Test-WindowsSignatures.ps1` also fails a release whose signing certificate is listed neither by thumbprint nor by name, because installed versions could not update to it.

### Certificate changes

1. Get the new certificate, or decide the new signing service, before the old certificate expires (currently 2027-10-11).
2. Add its thumbprint or name to `update-signers.txt` and publish a release that is still signed with the old certificate.
3. Sign later releases with the new certificate, and update `deploy/windows/signing-certificate.txt` for the release pipeline as before.
4. A computer that skipped the release from step 2 refuses the first installer signed with the new certificate. It shows the download-page link instead, and that one version is installed manually.

The right kind of entry depends on the certificate:

- **Certum renewal:** with the name listed, a renewal under the same name needs no change at all.
- **SignPath Foundation:** list the name `SignPath Foundation`, because its certificates are renewed on SignPath's schedule. The name is the publisher of every project SignPath signs, so with it the check proves only that SignPath signed the installer.
- **Azure Artifact Signing:** certificates are short-lived, so list the validated name, not thumbprints.

Entries of retired certificates can be removed in a later release.

## Restart to update

The **Restart to update** button in About is the operator's consent; there is no further confirmation. Clicking it runs these steps:

1. Re-check the installer's SHA-256.
2. Write `Updates/pending-update.json` with the old and new versions, the path of the open series (if any) and the installer log path.
3. Close the main window through its normal `Closing` handler (`CanLeaveDrawInput`, `FlushRaceInformationAsync`, `StopTimingForCloseAsync`). If the close is refused, delete the pending file and stay in the ready state. The reason is shown as for any refused close.
4. In `App.OnExit`, after `Dispose()` has stopped the live control panel, workers, local server and devices, start the installer:

   `OpenSkiTime-{version}-win-x64-setup.exe /SILENT /NOCANCEL /NORESTART /CLOSEAPPLICATIONS /LOG=<Updates>/install-{version}.log /UPDATE=1 /WAITPID=<process id>`

   - Start the installer as a plain child process, never through `OwnedProcessJob`. Its kill-on-close job would end the installer together with the application.
   - Do not pass `/SUPPRESSMSGBOXES`. The operator is present and must see an installer error instead of a program that silently disappears.
   - Do not pass `/DIR`. Inno Setup reuses the existing installation directory.
5. The installer waits for the application process to exit, installs with a progress window and starts `OpenSkiTime.Desktop.exe --after-update`.
6. Only a start with `--after-update` reads `pending-update.json`, and it deletes the file. A normal start leaves the file alone, for example another window opened while the installer runs.
   - If the running version is the new version, the status line says `Updated to X.Y.Z.` For the rest of the session, About shows `Updated from A.B.C` with **What's new**. The series is reopened through the File → Open recent path, and the installer is deleted.
   - Otherwise the status line shows the error `The update to X.Y.Z did not finish. Installer log: <path>`.

If installation fails, Inno Setup shows its own error and does not start the application. The verified installer stays in `Updates/`, so About offers **Restart to update** again at the next start. The next attempt overwrites the pending file.

Live publishing, device listening and capture stop as on any close, and the operator starts them again. The installer's Restart Manager closes any other running OpenSkiTime window, as in a manual reinstall today. If such a window cannot close, Inno Setup asks the operator.

### Installer changes

All changes are in `deploy/windows/installer.iss`:

- `[Setup]`: add `VersionInfoProductTextVersion={#AppVersion}`, so the signed version resource carries the full release version for check 4. Every installer the updater can be offered is built with it, because the updater installs only releases newer than itself.
- `[Code]`: `InitializeSetup` waits up to 60 s for the `WAITPID` process, using `OpenProcess`/`WaitForSingleObject` from kernel32. If the process is still running, setup stops with "OpenSkiTime is still running. The update was not installed." `IsUpdate` returns whether `{param:UPDATE|0}` is `1`.
- `[Run]`: add `Filename: "{app}\OpenSkiTime.Desktop.exe"; Parameters: "--after-update"; Flags: nowait; Check: IsUpdate`. It runs only after a successful installation. The existing `postinstall skipifsilent` entry stays for interactive installations.
- `CloseApplications=yes` stays as the backstop for a process that did not exit.

Interactive installations and the existing CI arguments behave as before.

## Copies the installer did not install

An installed copy has `unins000.exe` next to `OpenSkiTime.Desktop.exe`; the portable ZIP and development builds do not. For these copies, About shows the new version with **What's new** and a **Download page** link (`https://openskiti.me/download/`) instead of **Download update**. Running the installer from a portable folder would install a second copy elsewhere and leave the portable folder unchanged.

## User interface

- **Title-bar chip** (`UpdateChipButton`): a passive chip to the left of the window buttons that reads `Update available`, `Downloading update` or `Update ready`. It opens Settings → About and never takes focus. It is hidden while the application is up to date or when the check failed.
- **About, first card, under the version line:** `UpdateStatusText` shows one of these states:
  - `Up to date · checked 10:42`
  - `Checking for updates…`
  - `OpenSkiTime 0.6.0 is available`
  - `Downloading 0.6.0 · 120 / 290 MB`
  - `0.6.0 is ready to install`
  - `Could not check for updates · …`
  - `The update could not be verified · …`
  - `Updated from 0.5.2`

  Next to it are `CheckForUpdatesButton`, `CancelUpdateDownloadButton` and either `DownloadUpdateButton` or `RestartToUpdateButton` (primary action), plus the links `UpdateReleaseNotesLink` (**What's new**) and `UpdateDownloadPageLink`. Styles and tokens come from `Tokens.axaml` and `App.axaml`.
- **About, privacy card text:** "Event series, timing data and audit history stay in your local .ost files. Race data leaves this computer only through integrations you start, such as FIS services or live timing. OpenSkiTime checks openskiti.me for new versions without sending race data."

## Code placement

- **`OpenSkiTime.Application/Updates`:** `ReleaseVersion` (Semantic Versioning parsing and precedence), `UpdateManifest` and its parser, and the offer rule. No I/O; deterministic.
- **`OpenSkiTime.Desktop`:**
  - `UpdateClient`: manifest request and verified download, using an injected `HttpClient`.
  - `AuthenticodeVerifier`: `WinVerifyTrust`, the signer's thumbprint and common name, and the embedded `update-signers.txt`. Windows only, behind an interface.
  - The installer launcher.
  - `MainViewModel.Updates.cs`: state and commands.
  - `App.axaml.cs`: reading the pending file on a start with `--after-update`, and launching the installer after `Dispose`.
  - The title-bar chip in `MainWindow` and the About card in `SettingsView.axaml`.
- **Installer, website and release scripts:** `deploy/windows/installer.iss`, `deploy/windows/update-signers.txt`, `scripts/Test-WindowsSignatures.ps1`, `website/build.mjs`, `website/check.mjs` and `website/staticwebapp.config.json`.
- **Dependencies and Linux:** no new NuGet or npm dependencies. A future Linux build reuses the Application part and offers only the download-page link.
- **`OPENSKITIME_UPDATE_MANIFEST`:** for developers and automation only; not a user setting.
  - `off` disables checking. Tests, E2E (`tests/OpenSkiTime.Desktop.E2E/DesktopApp.cs`), demonstrations and screenshots set `off`.
  - An `https://` or `http://127.0.0.1` URL replaces the manifest address for rehearsals. Installer URLs are still derived from the version, and the installer must still pass every check.

## Tests

- **Application:**
  - Version precedence: `0.6.0` > `0.6.0-preview.2`, `preview.10` > `preview.9`, `0.10.0` > `0.9.0`; invalid input is rejected.
  - Manifest parsing: valid input; missing or wrong-typed fields; size ≤ 0; malformed hash; oversized input; unknown properties ignored.
  - No offer for an equal or older version.
- **Desktop**, with a fake HTTP handler, verifier and launcher:
  - An offline startup check shows only in About.
  - Available → download, then each verification failure deletes the file. This includes an older or preview installer offered as another version, for example a `0.6.0-preview.1` installer offered as `0.6.0`, which the product-version check rejects.
  - Cancelling deletes the partial file.
  - A refused close keeps the ready state and launches nothing.
  - An accepted close launches the installer with the expected arguments after `Dispose`.
  - A start with `--after-update` reports success (with reopen and cleanup) or the version mismatch. A normal start leaves the pending file untouched, as when another window opens during installation.
  - Copies without `unins000.exe` get only the link.
  - `off` makes no request.
- **Download**, against a loopback HTTP server: a redirect is followed, a redirect to HTTP is refused, the size limit and a hash mismatch stop the download.
- **Authenticode** (Windows):
  - A Microsoft-signed library from the test output is valid, and its thumbprint and common name are read.
  - A byte-modified copy and an unsigned file are rejected.
  - List matching: a thumbprint matches regardless of case and spaces, and a name matches exactly. Comments and blank lines are ignored. An unlisted signer is rejected.
- **Release pipeline:** `Test-WindowsSignatures.ps1` fails when the signing certificate is missing from `update-signers.txt`.
- **Installer** (`Test-WindowsInstaller.ps1`, in the unsigned and signed workflows): run update mode while a placeholder process is alive, with `OPENSKITIME_UPDATE_MANIFEST=off` and a temporary `OPENSKITIME_LOCAL_DATA`. Check that:
  - installation waits for the placeholder to exit;
  - the log is written to a path that contains a space;
  - `OpenSkiTime.Desktop.exe --after-update` is started again from the installation directory;
  - the installer's product version is the full release version.

  The existing reinstall and uninstall-preservation checks are unchanged.
- **Website** (`scripts/tests`): a manifest is written for a stable release but not for a preview, and the build fails without a valid digest.
- **Release rehearsal:** once, before the first stable release that contains the updater, because a broken updater cannot update itself.
  1. Install signed `X.Y.Z-preview.1` on a clean computer.
  2. Publish `X.Y.Z-preview.2`.
  3. Serve a hand-written manifest for preview.2 locally, with size and digest from `gh release view`.
  4. Start preview.1 with `OPENSKITIME_UPDATE_MANIFEST` pointing to that manifest, then run **Download update** and **Restart to update**.
  5. Check that a modified installer is rejected.

  After that release, step 8 of the release checklist includes updating a test computer from the previous version through About.

## Risks and limitations

- Every update downloads the full installer, about 290 MB today.
- Installation overwrites files in place. A power cut or forced shutdown during installation can leave a broken installation. Running the installer again repairs it: the installer stays in `Updates/` until the update succeeds, and is otherwise available from the download page.
- Files that a newer version no longer contains stay in the installation directory, as with a manual reinstall today.
- Versions released before the updater must be updated manually once.
- A computer whose list does not contain the certificate of a new release refuses it and needs one manual installation (see [Certificate changes](#certificate-changes)).
- A listed name is trusted from any CA. With `SignPath Foundation` listed, any installer SignPath signed for any project passes check 3. A certificate issued to a namesake with exactly the same name would pass too. Reaching users would still require control of the GitHub repository.
- If GitHub stops publishing asset digests, the website build must take the hash from `SHA256SUMS.txt` instead.
