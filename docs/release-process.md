# Release process

This is the maintainer checklist for publishing a desktop application release (`vX.Y.Z`) or a live timing server release (`live-vX.Y.Z`). Build, packaging, security scanning and deployment mechanics are described in [website, live hosting and Windows releases](website-and-releases.md) and [software supply-chain checks](software-supply-chain.md).

## What gets released

| Product | Tag | Changelog | GitHub release | Triggered workflow |
|---|---|---|---|---|
| Desktop application (installer, portable ZIP, local live server) | `vX.Y.Z`, `vX.Y.Z-preview.N` | [CHANGELOG.md](../CHANGELOG.md) | "OpenSkiTime vX.Y.Z" with installer, ZIP, SBOM, CVE reports and checksums. Stable versions are marked *Latest*. The website download offers the newest stable version, or the newest preview while no stable version exists. | `windows-release.yml` builds and tests; `windows-sign.yml`, started by the maintainer, signs and publishes |
| Hosted live timing server (`live.openskiti.me`) | `live-vX.Y.Z` | [CHANGELOG-LIVE.md](../CHANGELOG-LIVE.md) | "OpenSkiTime Live live-vX.Y.Z" with notes and the deployed image digest, no files. Created with *Latest* disabled (GitHub still shows it as latest until a stable application release exists; the website ignores it). Created only after a successful deployment. | `live.yml` |

Nothing is released automatically by merging. Pull requests, master merges and manual `live.yml` dispatches create no GitHub release. An application release needs a pushed tag and the maintainer's signing code; a live server release needs a pushed tag. Website content changes still deploy on merge; that is not a release.

Release notes are generated by `scripts/release-notes.mjs` from the changelog section at the tagged commit. Application notes have an **Application** section (the changelog entry), a **Live timing** section (live protocol and compatible server releases), and fixed installation and verification sections. A tag without a dated, non-empty changelog section fails before building.

## Versioning

Both products use [Semantic Versioning](https://semver.org/) `MAJOR.MINOR.PATCH`, numbered **independently**. A live server fix does not require an application release and vice versa.

- **Application:** `VersionPrefix` in `Directory.Build.props` is the single source and must equal the tag version without its pre-release suffix (`Assert-ReleaseSource.ps1` enforces this). Before 1.0: MINOR for features or `.ost` format changes, PATCH for fixes. From 1.0: MAJOR for incompatible changes. Use `-preview.N` for releases intended for rehearsal before the stable version.
- **Live server:** MINOR for new server behavior, PATCH for fixes and deployment changes.
- **Live protocol:** `LiveProtocol.Version` in `OpenSkiTime.LiveTiming.Contracts` is the compatibility contract between a published application and a server. Publishers send it in the `X-OpenSkiTime-Live-Protocol` header; the server returns its own version in that header and in `/health`, and refuses a different declared version with HTTP 426. Increment it only for an incompatible change to the publishing API or payloads. A compatible additive change keeps the version.

Every application changelog section states the live protocol it uses ("live protocol N"). Every live changelog section starts with `Live protocol: N`. The generated application notes list the compatible server releases from those lines.

### Changing the live protocol

The hosted server must keep serving installed applications. A protocol increment therefore needs a server that accepts both the old and new version before an application using the new version is released:

1. Release a live server that accepts protocols N and N+1.
2. Release the application using N+1.
3. Remove N from the server only in a later release, after announcing it in the changelogs.

This sequence is not implemented yet because only protocol 1 exists. Implement multi-version acceptance in the server with the first increment.

## Development phase and series file migrations

OpenSkiTime is in development and is not yet intended for timing real races. It will be tested at real competitions during the 2026-27 season. Every application release says this in a fixed *Development status* section of its notes (`scripts/release-notes.mjs`) and on the download page. During this phase releases are `0.x` previews for rehearsal and evaluation, and there is no migration code. A version with breaking changes to the `.ost` format refuses to open files created by earlier versions and leaves them unchanged; the operator creates a new series file. Keeping older versions and their files lets earlier series still be opened.

Each changelog section states whether the version breaks `.ost` compatibility ("Series files from earlier versions cannot be opened; create a new series file") or keeps it.

Database migrations are introduced later, before the first release intended for real race use. Their design is decided then.

## Changelog practice

Add user-visible changes under `## [Unreleased]` in the relevant changelog during normal pull requests, using the [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) groups *Added*, *Changed*, *Fixed*, *Removed* and *Security*. Write for operators, not developers: describe behavior and limitations, not implementation. Do not mention internal planning, agent workflows or personal data. Dependency and CI-only changes need no entry unless they affect users.

## Application release checklist

1. **Decide the version.** Confirm that `.ost` compatibility and migration expectations for the version are stated in the changelog. Until migrations exist, state whether the version breaks `.ost` compatibility and requires a new series file.
2. **Rehearse on a clean Windows machine** using a CI build from the release candidate commit (the installer of a previous preview release, or a local `Package-Windows.ps1` build). CI does not cover the desktop GUI, physical timing devices or a Cloud publishing rehearsal against `live.openskiti.me`.
3. **Prepare a release pull request** to master:
   - Move `## [Unreleased]` entries into `## [X.Y.Z] - YYYY-MM-DD` (or `X.Y.Z-preview.N`) and keep an empty `## [Unreleased]` heading. Update the link references at the bottom.
   - State the live protocol ("This version uses live protocol N.").
   - Bump `VersionPrefix` if the core version changes.
   - Check the notes locally: `node scripts/release-notes.mjs app X.Y.Z release-notes.md`.
4. **Merge** after the required checks pass.
5. **Tag the merged master commit** and push the tag. Tags are annotated and never moved:

   ```powershell
   git switch master
   git pull --ff-only
   git tag -a vX.Y.Z -m "OpenSkiTime X.Y.Z"
   git push origin vX.Y.Z
   ```

6. **Wait for `Windows release build`.** It validates the tag, tests, publishes the unsigned application, and checks an unsigned installer and portable package. It publishes nothing. Its unsigned build is kept for one day.
7. **Sign and publish** from a machine with an authenticated `gh` and the SimplySign mobile app (see [Code signing](#code-signing-certum-simplysign)):

   ```powershell
   node scripts/release-signing.mjs submit vX.Y.Z
   ```

   Enter the current SimplySign code when the script asks for it, usually one to two minutes later. The script ends when the application files are signed. `Windows signing and release` then signs the installer, tests the signed package and installer, scans dependencies and publishes the release. Stable releases then rebuild the website download link.
8. **Verify the published release:** download the installer and `SHA256SUMS.txt` from GitHub into one folder and check them with the PowerShell command in the release notes' Verification section (or `sha256sum -c --ignore-missing SHA256SUMS.txt` on Linux), check that the installer's *Digital Signatures* tab shows a valid, timestamped signature by the project certificate, install it on a test machine, check Settings → About shows the version, and for stable releases check `https://openskiti.me/download/`.
9. If a problem is found after publication, do not replace files or move the tag. Publish a new PATCH or preview version. A broken release can be marked as a prerelease and its notes edited to point to the fix.

## Live server release checklist

1. Move the `## [Unreleased]` entries in `CHANGELOG-LIVE.md` to `## [X.Y.Z] - YYYY-MM-DD`, starting with `Live protocol: N`. Merge to master.
2. Avoid race windows: deployment can reset RAM state, and active publishers then resend their snapshots.
3. Tag the merged master commit and push it:

   ```powershell
   git tag -a live-vX.Y.Z -m "OpenSkiTime Live X.Y.Z"
   git push origin live-vX.Y.Z
   ```

4. `Live deployment` builds and scans the image, deploys it with automated acceptance and rollback, then creates the GitHub release. If deployment is disabled or fails, no release is created; fix the cause and publish a new PATCH tag.

## Code signing (Certum SimplySign)

Windows releases are signed with the maintainer's Certum *Open Source Code Signing in the Cloud* certificate. The private key stays in Certum's cloud HSM. Using it needs the account e-mail and a one-time code from the SimplySign mobile app, valid for about 30 seconds. Signing uses [ssign](https://github.com/Le-Syl21/ssign), an open-source command-line client for the SimplySign cloud service, pinned to a release checksum in `.github/actions/setup-ssign`. ssign is not made or supported by Certum. If the service changes and ssign stops working, sign by hand with SimplySign Desktop and `signtool` until the client is updated. The public policy is on the website at [/code-signing/](https://openskiti.me/code-signing/) and must stay accurate.

No long-lived signing secret is stored in GitHub. The TOTP seed behind the mobile app is never exported, so every release needs a fresh code from the maintainer.

### What is signed

`scripts/WindowsSigning.psm1` defines the scope: OpenSkiTime's own `OpenSkiTime.*.exe`/`.dll` files (including the copies used by the live control panel), `TimyUsbHost.exe`, the installer and its uninstaller. The .NET runtime keeps Microsoft's signatures; third-party libraries are not re-signed. Signatures use SHA-256 and an RFC 3161 timestamp from `time.certum.pl`, so they stay valid after the certificate expires.

The expected certificate's SHA-1 thumbprint is pinned in `deploy/windows/signing-certificate.txt`. A signature by any other certificate, or one without a timestamp, fails the release. Update the thumbprint in a reviewed pull request when the certificate is renewed.

### Signing code handshake

`windows-sign.yml` runs on a GitHub-hosted Windows runner in the `code-signing` environment. `scripts/release-signing.mjs` implements both sides:

1. The maintainer runs `node scripts/release-signing.mjs submit vX.Y.Z`. The script refuses to run unless `gh` is signed in as the operator, identified by numeric GitHub user ID (`operator` in the script, user 259367049, `tnakeli`). It checks that the tag's `Windows release build` succeeded and has an unexpired `windows-unsigned` artifact, then dispatches `windows-sign.yml` on master.
2. The job validates the tag (`Assert-ReleaseSource.ps1 -SigningTag`) and finds the tag's successful build run. It downloads that run's `windows-unsigned` artifact by artifact ID and checks the ZIP against the SHA-256 digest GitHub recorded at upload. It then installs ssign.
3. The job creates an RSA-3072 key pair and a random 128-bit request ID. The private key and request ID stay in the runner's temporary directory. The request is uploaded as the workflow artifact `signing-request-<attempt>`. It contains the public key, workflow path, signing run ID and attempt, request ID, tag, commit, operator ID, and the build run, artifact ID and digest being signed. Only that run can add artifacts to itself, so the key's origin needs no separate signature.
4. The script accepts only a signing run of `windows-sign.yml` on master that the operator dispatched. It downloads the request ZIP and checks it against the artifact's recorded SHA-256 digest. It then verifies every request field against the GitHub API, including that the build run, artifact ID and digest are the tested build of the tag. Only then does it ask for the code. It encrypts the code with RSA-OAEP (SHA-256) together with the request ID, run ID and attempt, and posts the ciphertext as a commit comment on the release commit, headed with the run, attempt and request ID.
5. The job polls all pages of the release commit's comments. It accepts only a comment by the operator's numeric user ID whose header and encrypted payload both name its own request ID, run and attempt and that decrypts with its key. It then deletes the private key. It masks the code in the log and runs ssign. The first ssign call logs in and caches a session of about 20 minutes on the runner; later calls, including Inno Setup's `SignTool`, reuse it.
6. The script deletes the comment once the signing step has finished and reports the result.

Anyone can read the ciphertext, but only that runner can decrypt it, and the code is single-use. Comments by anyone else, including an account that later takes over the login name, are ignored. A code can be used only by the one request it was encrypted for, and that request names the exact tested artifact by digest. A forged request cannot reach the script, because the key must come from the signing run's own artifact. At worst, someone can obstruct one signing attempt. If the code is late or wrong, the step fails: re-run the failed jobs and submit again with `node scripts/release-signing.mjs submit vX.Y.Z --run <run-id>`. Each attempt creates a new key.

### Packaging order

The Inno Setup uninstaller can be signed only while the installer is compiled, so the final installer is built in the signing job:

1. `windows-release.yml` runs `Package-Windows.ps1 -Stage Publish` and uploads the unsigned app directory as `windows-unsigned` before any test runs packaged processes. It then assembles an unsigned installer and ZIP from a copy for acceptance testing.
2. `windows-sign.yml` signs the application files (`Sign-WindowsPackage.ps1`) and runs `Package-Windows.ps1 -Stage Assemble -SignTool <ssign>`. That builds the ZIP from the signed files and compiles the installer with `SignTool=ssign`, which signs the uninstaller and the installer. `SHA256SUMS.txt` is computed from the signed files.
3. `Test-WindowsSignatures.ps1` checks the app directory, the installer and the ZIP contents. The signed release files are uploaded. The package test and `Test-WindowsInstaller.ps1 -VerifySignatures`, which also checks the installed `unins000.exe`, then run on the signed files. The dependency scan runs on the signed ZIP before publication.

### One-time repository setup

- Environment `production-release`: deployment branches limited to `master`, because `windows-sign.yml` is dispatched on master and publishes from there. `deploy/azure/Configure-Repository.ps1` applies this policy and the `code-signing` policy below.
- Environment `code-signing` (created 2026-10-14): deployment branches limited to `master`, and environment variable `CERTUM_EMAIL` set to the Certum account e-mail. It needs no secrets and no reviewers; entering the code is the approval.
- `deploy/windows/signing-certificate.txt` contains the certificate thumbprint. A change of operator also changes `operator` in `scripts/release-signing.mjs`. Read it from a file signed by hand with ssign: `(Get-AuthenticodeSignature file.exe).SignerCertificate.Thumbprint`.
- The maintainer's GitHub and Certum accounts use multi-factor authentication.
